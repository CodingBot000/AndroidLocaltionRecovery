# PR #9 G7 실기기 콜드 기동 최종 재시험

## 범위와 측정 계약

2026-11-27 KST에 기준 A `a732af2dddfb86514fbfa76a6d7971f31e8d23da`와 후보 C `ce617de21ffbf5485564c9d7bc589a3b6085c02c`를 이전 SM-G975N(Android 12/API 31·Exynos 9820·ARM64)에서 비교했다. 시작 PR head는 `3335ae957ded3a526b09517e98bc1cdd337a24be`였다. 이번 재시험의 범위는 G7 콜드 기동이다. 지도 전환과 주행은 최초 G7 자료를 사용한다. [최초 G7 본 측정과 첫 재시험](recovery-ui-physical-g7.md)

기존 A/C에서 사용한 Release 상속 profileable 대상 APK를 보관본에서 재사용하고 각 세트의 설치 후 SHA-256을 비교했다. 격리 빌드의 원본 계측 APK 두 파일과 단말에 설치된 계측 APK는 바이트 단위로 일치했다. 원본 `RefactorMapBenchmark#coldO10`의 AndroidX Benchmark 1.5.0, `StartupMode.COLD`, `CompilationMode.None()` 및 기존 대기 단언을 사용했다. 세트당 3회, A6→C6→C7→A7 순서로 기록했다.

AndroidX의 원래 TTID와 TTFD를 기준으로 세 번의 측정을 독립 비교한다. A 대비 후보 TTFD 중앙값이 10% 이상 증가할 때 조사하는 기존 기준을 적용한다. TTID는 첫 화면 프레임, TTFD는 앱의 완전 표시 보고가 반영된 프레임까지의 AndroidX 지표다. 이 앱은 현재 실행의 O10 지도 지오메트리와 프레임 준비 신호를 받은 뒤 `ReportDrawnWhen` 조건이 충족된다. 원본 trace의 시작·첫 프레임·`reportFullyDrawn()`·후속 RenderThread 완료를 대조했다. 지도 지오메트리 단독 시간에는 원본 trace의 별도 구간 표시가 없으므로 첫 표시→완전 표시 보고를 준비 관련 구간으로 다룬다. [AndroidX StartupTimingMetric](https://developer.android.com/reference/kotlin/androidx/benchmark/macro/StartupTimingMetric)

## JIT와 첫 화면·지도 준비 관련 구간

최종 12개와 이전 콜드 30개 trace의 AndroidX 1.5.0 시작·렌더 프레임 선택 규칙을 재현했다. 42개에서 원본 TTID·TTFD와 모두 일치했다. 일반 Perfetto 시작 모듈의 TTFD는 최종 12개 중 8개 일치, 3개 불일치, 1개 누락이었다. 최초와 첫 재시험의 원본 지표와 표본은 그대로 보존했다. 아래 구간은 AndroidX 계산과 대조를 마친 trace를 사용한다. [Perfetto 일반 시작 모듈](https://perfetto.dev/docs/analysis/stdlib-docs#androidstartup)

| 세트별 중앙값 (ms) | A6 | C6 | C7 | A7 |
|---|---:|---:|---:|---:|
| JIT 스레드 실행 합계 · `measureBlock` | 30.2 | 370.1 | 29.0 | 354.8 |
| 첫 표시 → `reportFullyDrawn()` | 728.1 | 1,201.9 | 765.4 | 1,059.7 |
| `reportFullyDrawn()` → 완전 표시 프레임 RenderThread 완료 | 64.5 | 50.5 | 63.8 | 62.8 |

빌드별 6회에서 첫 표시→완전 표시 보고의 중앙값은 A 882.5ms, C 1,007.9ms였다. 완전 표시 보고→프레임 완료는 A 63.6ms, C 62.2ms로 가까웠다. 첫 표시와 완전 표시 사이의 구간에는 지도 준비와 Compose·프레임 스케줄링이 함께 들어간다. 지도 준비 신호와 UIAutomator의 개별 단언 시각은 원본에 별도 표시가 없어 각 비용을 분리할 수 없다.

최종 12개의 TTFD와 JIT 실행 시간의 상관은 `measureBlock`에서 Pearson r=0.82였다. 시작부터 완전 표시 프레임까지만 집계해도 r=0.82였다. 최종의 A6·C7은 낮은 JIT 실행 시간, C6·A7은 높은 실행 시간과 긴 TTFD를 보였다. 최초 본 측정에서도 빠른 세트와 느린 세트가 두 빌드에 걸쳐 나타났고, 첫 재시험에서는 양쪽 모두 JIT 실행이 높은 구간에 모였다. JIT 스레드 실행 시간의 합은 벽시계 시간과 단위의 의미가 다르고, 이 관측으로 JIT 실행이나 실행 순서가 기동 차이를 일으켰다고 확정할 수 없다. [구간과 반복별 trace 집계](benchmarks/sm-g975n-pr9-g7-final-cold.json)

## 최종 판정과 복원

**G7 최종 판정은 INCONCLUSIVE다.** 최종 TTFD +9.0%는 기존 10% 조사 기준 이내였다. 최초 +30.7%, 첫 재시험 −4.8%, 최종 인접 쌍 +36.2%와 −27.5%에서 지연의 방향이 달랐다. 현재 자료로 지속적인 후보 고유 콜드 기동 회귀를 확인할 수 없다. 차이가 생긴 조건과 지도 준비 단독 비용은 미확정이다. G7 성능 계측은 이 결과에서 종료했다. G3·G8·G9는 기존 **INCONCLUSIVE**다. [전체 수용 게이트](recovery-ui-validation.md#f7--기존-pr과-수용-게이트)

원래 APK 6개와 계측 미디어 13개의 SHA-256, 벤치마크 대상을 제외한 기존 설치 경로와 데이터 디렉터리, 앱 중지 상태, 홈 화면·잠금·화면·네트워크·위치 설정을 확인했다. 벤치마크 전용 대상의 내부 데이터·ART 프로필은 `CompilationMode.None()`과 이전 승인 범위에 따라 초기화됐다. 원본 trace 12개와 결과 JSON 4개는 로컬 보존 파일과 SHA-256을 대조한 뒤 단말에서 정리했다.
