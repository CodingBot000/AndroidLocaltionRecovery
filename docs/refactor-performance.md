# 지도 렌더링 및 위치 매칭 성능 비교

[README](../README.md) · [지도 설계](korea-map-design.md) · [장애 분석](stability-investigation.md) · [최신 플랫폼 비교](verification.md#성능-비교와-자원)

## 결과 요약

**채택된 개선:** 도로 매칭의 Spatial Grid, 비동기 지도 준비 및 렌더링 레이어 분리. 각 비교의 기준 SHA·단말·표본은 서로 다르다. 최근 실기기 후보 실험은 [렌더링·메모리 RCA](rendering-memory-rca.md)에서 별도로 확인할 수 있으며, 그 후보는 채택되지 않았다.

### 초기 리팩터링 (P17–P24)

| 개선 | 관측 결과 | 트레이드오프 |
|---|---|---|
| 위치 매칭 SpatialGrid | O10 42.30 → 7.73µs, 기존 판정 일치 | 구축 19.87ms, 생존 힙 약 1.16MB 증가 단일 표본 |
| 지도 준비 분리 | 전환 CPU P50 72.1 → 11.6ms | 준비 및 전환 총시간 증가 |
| 렌더링 레이어 분리 | 주행 시한 초과 P95 596.6 → 556.6ms | 주행 CPU P95 412.0 → 415.5ms, 지연 지속 |

P17–P24의 비교이며 P25–P32와 기준선이 다르다. Android는 API 36 에뮬레이터 3회씩, JVM 매칭은 별도 7회 비교다. 최신 상세 지도 실기기 성능을 보장하지 않는다.

## 측정 환경과 방법

기준선은 원격 main `f825195`에 마커 오버레이 변경을 포함한 `653e311`이다. 후속 측정은 리팩터링 코드 `33c5d79`에서 실행했다. API 36 ARM64 에뮬레이터, 1080×2400 세로 화면, 동일한 지도·배속 1×·벤치마크 APK 유형·`CompilationMode.None()` 조건에서 각 Macrobenchmark를 3회 실행했다. O10 콜드 실행, O10→O07 전환, O10 주행 첫 8초 동안의 확대·Overview·Follow를 별도로 측정했다. O07 전환은 두 빌드에 같은 벤치마크 전용 시나리오 선택 진입점을 사용해 메뉴 애니메이션을 제외했다.

콜드 TTID와 지도 준비 완료 시간은 늘었다. 지도 전환 중 프레임 CPU와 시한 초과는 개선됐지만, 준비가 끝날 때까지의 총시간은 증가했다. 인덱스 생성과 화면에 지도가 실제로 준비됐을 때 완료를 보고하는 방식이 로딩 구간에 포함된다. 주행 CPU P95는 소폭 늘었고 시한 초과 P95는 감소했다. 작은 표본이며 에뮬레이터 특성이 반영된 값이다.

| 상태 | 기준선 PSS / Dalvik 할당 | 리팩터링 PSS / Dalvik 할당 |
|---|---:|---:|
| 첫 O10 | 97,737 / 33,601KiB | 103,880 / 36,857KiB |
| 첫 O07 전환 | 113,287 / 5,485KiB | 118,728 / 5,714KiB |
| 교차 전환 3회 후 O07 | 98,109 / 5,517KiB | 100,460 / 5,730KiB |
| 교차 전환 3회 후 O10 | 180,119 / 33,661KiB | 188,772 / 36,905KiB |

같은 지도에서 만든 인덱스와 가시 Path를 재사용한다. 위 메모리는 지도 준비 직후의 단일 스냅샷이다. 반복 전환 후 O10의 할당 Dalvik 힙은 첫 O10의 할당량과 비슷했고, PSS는 늘었다. 장기 메모리 누적이나 누수 판정에는 별도 반복 표본이 필요하다.

## Perfetto 관찰

양쪽 O10 주행 벤치마크의 두 번째 trace에서 `measureBlock`에 있는 앱 surface frame과 스케줄 실행을 확인했다. UI 스레드 실행 시간은 543.83→492.53ms였고 RenderThread는 8,959.32→8,514.30ms였다. 기준선과 후속 trace에 `App Deadline Missed` 및 `SurfaceFlinger CPU Deadline Missed`가 반복해서 나왔다. 이 표본에서 가장 많은 실행 시간은 RenderThread에 있었으며, 지도 레이어별 함수 비용은 별도 계측하지 않았다. trace 원본은 로컬 `build/reports/map-refactor/{baseline,after}-ride.perfetto-trace`에 보존했다.

## JVM 도로 매칭

| 지도 | 전체 도로 / 관측 / 평균 후보 | 구축 시간 | 전체 순회 중앙값 | 인덱스 중앙값 |
|---|---:|---:|---:|---:|
| O07 | 657 / 101 / 18.2 | 2.62ms | 15.82µs | 11.07µs |
| O10 | 18,490 / 160 / 15.3 | 19.87ms | 42.30µs | 7.73µs |

두 실제 지도에서 관측별 후보 집합과 보정된 위치, 점수, 보류 판정을 비교했다. 워밍업 후 전체 입력 매칭을 번갈아 7회 측정한 관측당 시간 중앙값이다. JVM의 GC 후 생존 힙 단일 표본에서 O10 인덱스 생성 직후 약 1.16MB 증가가 관찰됐다. O07 표본은 GC 변동이 커서 인덱스의 별도 메모리 비용을 산정하지 않았다.

## SM-G975N / API 31 실기기 OSM 비교

API 31 물리 단말에서 기준선 `653e311`과 최신 운영 소스 `d0b3822`를 같은 벤치마크로 시나리오별 9회 평가했다. O10 콜드 TTID 중앙값은 545.1→464.3ms, TTFD는 1,871.8→1,343.9ms였다. O10 주행·카메라 Frame CPU P95는 86.0→101.8ms였고 시한 초과 P95는 78.8→102.1ms였다. 단말, 컴파일 조건, 유효 표본과 제외 사유는 실기기 최종 보고서에 기록했다. [실기기 보고서](real-device-final-validation.md#rd3-실제-osm-성능)

`a067a97`을 기준으로 다시 측정한 렌더링 분포와 반복 재생 메모리는 후속 조사에 기록했다. [렌더링·메모리 RCA](rendering-memory-rca.md)
